HUMAN-READABLE CODE RULES
=========================

1. Use descriptive domain names. Prefer `getCurrentAgentWallet` over `getData` and
   `PayoutRequestForm` over `FormComponent`.
2. Keep route files thin. A `page.tsx` composes a screen; it must not contain raw
   HTTP calls, large validation blocks, or unrelated business rules.
3. Keep API calls inside feature API modules. Do not call `fetch` directly from UI
   components.
4. Keep query keys, API functions, schemas, hooks, and visual components separate.
5. Prefer small explicit components over one highly configurable mega-component.
6. Do not put Customer, Agent, and Admin behavior into one component with many role
   branches.
7. Do not use `any`. Model request and response DTOs from the implemented backend
   contracts.
8. Do not duplicate API DTO definitions between applications. Shared contracts have
   one owner in `packages/contracts`.
9. Do not store server data in a global client store. Use server components where
   appropriate and TanStack Query for interactive server state.
10. Keep client components at the smallest practical boundary. Add `use client`
    only where browser state, events, or client hooks are required.
11. Name booleans as questions: `isSubmitting`, `canApprove`, `hasNextPage`.
12. Extract complex conditions into named functions. JSX must describe the screen,
    not hide business logic.
13. Comments explain decisions or constraints, not obvious syntax.
14. Avoid barrel files that conceal circular dependencies. A package may expose a
    deliberate public API, but features should use direct, understandable imports.
15. Format all TypeScript, TSX, CSS, JSON, and Markdown with the repository's pinned
    Prettier configuration. TypeScript strict mode must remain enabled.
16. Every mutation must expose disabled/loading, validation, success, conflict,
    forbidden, and unexpected-error behavior.
17. Never invent endpoints, statuses, permissions, metrics, or DTO fields. Record an
    API GAP when the backend cannot support the required interaction.

Recommended feature structure:

features/<feature-name>/
    api/
        <operation>.ts
        query-keys.ts
    components/
    hooks/
    schemas/
    types/
    <FeatureName>Page.tsx

SUB-PHASE 12.2 - IMPLEMENT SHARED PLATFORM PACKAGES
====================================================

12.2.1 `contracts`
    - Model implemented backend DTOs, enums, pagination, and Problem Details.
    - Preserve backend nullability and enum representation.
    - Do not create frontend-only fields inside API DTOs.

12.2.2 `api-client`
    - Configure the API base URL in one place.
    - Support request serialization, response parsing, cancellation, and timeouts.
    - Include credentials when the selected authentication transport requires them.
    - Acquire and send antiforgery tokens for cookie-authenticated mutations.
    - Normalize 400, 401, 403, 404, 409, 422, 429, timeout, network, and 500 errors.
    - Preserve validation error details without exposing stack traces.

12.2.3 `auth`
    - Load the current identity from the implemented current-user endpoint.
    - Model authentication separately from authorization.
    - Distinguish 401 session expiration from 403 insufficient permission.
    - Provide role/capability guards for routes and actions.
    - Logout/revoke the current session through the backend contract.

12.2.4 `organization-context`
    - Resolve Organization from the request hostname or supported slug route.
    - Load persisted public branding and locale configuration.
    - Never require ordinary users to enter OrganizationId, CustomerId, or AgentId.
    - Prevent cached Organization data from leaking between hosts.

12.2.5 `design-system`
    - Implement accessible typography, spacing, color, focus, status, and elevation
      tokens.
    - Implement reusable Button, Input, Textarea, Select, Checkbox, RadioGroup,
      Dialog, Drawer, Dropdown, Tabs, Badge, Alert, Toast, Skeleton, Breadcrumb,
      Pagination, DataTable, EmptyState, ErrorState, and ConfirmationDialog.
    - Keep business workflows out of the design-system package.

12.2.6 `observability`
    - Generate or propagate a correlation identifier where supported.
    - Record route performance and normalized client failures without recording
      credentials, tokens, addresses, or other sensitive payloads.

Completion checks:
    - No application duplicates transport, current-user, Organization resolution, or
      primitive UI logic.
    - Shared packages contain no Agent/Admin/Customer workflow components.
    - Package APIs are documented through names and types rather than excessive
      comments.

SUB-PHASE 12.9 - PERFORMANCE, SECURITY, AND OBSERVABILITY
=========================================================

12.9.1 Performance
    - Use server rendering for public catalog content where compatible with tenant
      resolution and personalization.
    - Use deliberate cache/revalidation rules; never cache private user data across
      sessions or Organizations.
    - Lazy-load large visualizations and non-critical Admin tools.
    - Measure route loading, interaction latency, bundle size, and Core Web Vitals.

12.9.2 Security
    - Keep provider secrets and backend credentials out of browser bundles.
    - Do not persist bearer tokens in localStorage when secure cookie transport is
      selected.
    - Use the backend antiforgery contract for cookie-authenticated mutations.
    - Do not log tokens, payment data, addresses, or private customer information.
    - Treat frontend guards as UX only; backend policies remain authoritative.

12.9.3 Observability
    - Record application, route, release, and correlation context.
    - Capture normalized failures and performance without sensitive request bodies.
    - Provide useful production error boundaries rather than exposing raw exceptions.

Completion checks:
    - No secret is present in generated client JavaScript.
    - Private responses are not shared through server or CDN caches.
    - Performance budgets are measured in production builds.
