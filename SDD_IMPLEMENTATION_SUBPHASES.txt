MODULAR MLM — SDD IMPLEMENTATION SUB-PHASES
===========================================

Purpose
-------
This roadmap closes the gaps found during the full codebase-to-SDD audit.
Complete the sub-phases in order unless a dependency explicitly allows parallel work.

Rules for every sub-phase
-------------------------
1. Keep Domain independent of Application, Infrastructure, and Web.
2. Keep commands, handlers, validators, queries, and DTO models in separate files.
3. Queries with DTOs place DTO files under a Models subfolder.
4. Enforce authorization and organization ownership inside Application handlers.
5. Treat Web role checks as UX/routing protection, not the only authorization boundary.
6. Use decimal for money and volume. Never use float or double for financial values.
7. Preserve immutable financial ledgers; corrections must create linked reversal entries.
8. External provider calls must be idempotent and must not remain inside long DB transactions.
9. Add database constraints as the final concurrency and idempotency protection.
10. A feature is incomplete until Domain, Application, Infrastructure, Web, migration, and tests are covered where relevant.

SUB-PHASE 1 — AUTHORIZATION AND TENANT-SAFETY HOTFIX
=====================================================

1.1 Introduce a reusable Application authorization service/policy
    It must answer:
    - Is the current user the requested Customer?
    - Is the current user the requested Agent?
    - May the current user administer this Organization?
    - May the current Agent inspect the requested downline/network node?

1.2 Fix Agent application impersonation
    - ApplyAsAgent must derive UserId from IUser/current authentication.
    - Do not accept another user's identity as an ordinary request field.
    - Administrator-created applications, if required, must use a separate Admin command.

1.3 Fix checkout and payment-session ownership
    - Checkout must derive or verify CustomerId from the authenticated user.
    - Payment-session creation must verify that the current customer owns the order,
      or that the caller is an authorized Organization Administrator.
    - Validate every order and customer against OrganizationId.

1.4 Protect Agent-scoped reads
    Apply ownership/visibility checks to:
    - GetWalletSummary
    - GetAgentEarningsSummary
    - GetAgentCommissionHistory
    - GetCommissionDetails
    - GetBinaryVolumeSummary
    - GetPairingHistory
    - GetBinaryTree
    - GetDownline
    - GetDirectPlacementChildren
    - GetPlacementAncestors
    - GetDirectRecruits
    - GetAgentLegSummary
    - Referral dashboard/link/code operations

1.5 Protect administrator mutations inside handlers
    Add Application-layer Organization-admin checks to:
    - Product and commission-profile mutations
    - Commission-plan mutations
    - Agent lifecycle and placement mutations
    - Organization settings mutations
    - Refund and reconciliation operations

1.6 Add functional security coverage
    Test:
    - Agent A cannot read Agent B's wallet, earnings, commissions, or private network.
    - Customer A cannot create a payment session for Customer B's order.
    - A user cannot submit an Agent application for another user.
    - An Administrator cannot access another Organization.
    - Route-role checks and handler ownership checks both apply.

Completion checks
    - No protected handler trusts route/body identity without verification.
    - Cross-Organization and cross-user tests pass on PostgreSQL.
    - Unauthorized, forbidden, and not-found behavior is consistent.

Sub-phase 1 implementation record
    - Reusable request-scope authorization verifies Organization Administrator,
      Customer, Agent, Order, Payout, and downline visibility boundaries.
    - ApplyAsAgent derives UserId from IUser and no longer accepts it from clients.
    - Checkout and payment-session requests verify Customer/Order ownership within
      OrganizationId before their handlers execute.
    - Agent-private reads use IAgentScopedRequest.
    - Externally callable Administrator mutations use IOrganizationAdminRequest;
      internal webhook and worker commands remain separate.
    - PostgreSQL functional tests cover cross-user, cross-Organization, route-role,
      handler-scope, no-write-on-forbidden, and 401/403/404 behavior.
